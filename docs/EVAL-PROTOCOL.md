# Identity-first design evaluation protocol

**Status:** methodology only; no cross-model, real-owner or rendered three-way benchmark has been executed solely by adding this file.

## Tasks

Use permissioned, source-grounded briefs for at least three different developer/creator identities in the same broad category, plus one framework/SaaS task. Record real first-party artifacts: biography explicitly supplied by the owner, current writing samples, project work, screenshots, supported product behavior. Redact private identifiers and never manufacture author traits.

Compare the same model/tool version and budget under three conditions:

1. Generic design baseline (no MungTangE prompt).
2. Current MungTangE six-gate design prompt with identical source availability.
3. Identity-led MungTangE using source signals, three competing directions, Brand DNA, substitution challenge and screenshot critic.

Where a task requests three designs, require **three runnable, actually captured previews** with the same real content and constraints. Written concept descriptions alone cannot score for visual diversity.

## Independent scoring rubric

| Aspect | What the reviewer must actually see |
| --- | --- |
| Author distinctiveness | Source-backed signals materially change hero, content order, project proof and visual language |
| Substitution resistance | With the name/photo replaced, at least two substantial claims/visual proofs would need redesign |
| Direction diversity | Three captures differ in composition, typography, information hierarchy and evidence; not palettes |
| Editorial fidelity | Actual author vocabulary and project artifacts rather than generic developer slogans |
| Mobile reading comfort | Human review of 390px PNG, text size, line height, contrast, code and zoom at 200% |
| Interaction and accessibility | Keyboard task completion, focus, zoom, error/empty states and no severe blockers |
| Costs and repeatability | Actual generation attempts, time, token usage, build output and reproducible checks |

Blind reviewers should not see variant labels; randomize presentation order and report disagreements. Source-derived claims and layout bugs must be independently checked. Publish raw task identifiers, prompt variants, tools, viewport/browser details, screenshot paths, objective test results and unresolved defects.

## Stop conditions

No score when the task was not rendered, screenshots weren't opened, identity facts were unavailable, browser tests were not run, or reviewers were not independent. Do not turn a passing structural JSON validator or pixel-change percentage into a visual/brand quality score. Critical broken user flows or deceptive factual claims block ship even after a high subjective rating.
